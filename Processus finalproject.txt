UML : 

To design UML, we first listed the business objects present in the statement to help us create the diagram and the logical data model (LDM).
Each class has a primary key. We notice that Individual and Community share common attributes and can both send messages.
In this case, we create a Superclass which we name: 'Connectable_Entity' where they inherit from.

    Connectable_Entity (#idEntity: Integer, name: String,  public_key_G1: String )

    Individual (#idEntity : int, email : String)	
    Community  (#idCommunity : int)

    Message    (#idMessage: Integer, content: String,  send_date: DateTime)
Messages are separated in order to support message history, references between messages...

The exclusion vote cannot be represented by a simple link, as it must contains information. 
We are creating an association class. 

    Opposition (#idOpposition: int, vote_date: DateTime, reason: String)
The vote is made by an individual against another one within a community.

    Skills  (#idSkill : int, name : String)
    
    Geolocalisation (#idGeolocation: int, statement_date: DateTime, latitude: Float, longitude: Float,  link: String )

    Service (#idService : int, titre : String, description : String,idIndividual)

There are 3 types of services and they have characteristics, so we make 3 classes that inherit from the common attributes of Service

    Exchange_Service (#idService : int, description_expectation: String )
    Commercial_Service (#idService : int, price: Float )
    Free_Service (#idService : int )

Association classes:
For (many to many) relations , we create a new class:

    Master ( #idIndividual : int, proficiency_level : int)

between Individual and Skills 
We made this to link them to users with their specific proficiency level (0-5).

    Link (#idSource: int, description: String)

between 2 Entities
We moved the link here (instead of on Messages) so users can declare social ties like "neighbors" as described in the text.

    BelongTo (#idIndividual: int, isCreator: Bool)

between Individual and Community
We made this table to link people to communities and store the "isCreator" status.

SQL:  

SQL is written almost the same way as the MLD, but we create the tables and add the constraints.  
For example, you need to set NOT NULL for all attributes when no default value can be assigned.

Some writings are specific in PostgreSQL:
    TIMESTAMP for DateTime
    CAST for CONCAT
    REFERENCES for FOREIGN KEY

We thought about some constraints like :

The user can only enter an existing Geolocation with:
    CONSTRAINT check_latitude CHECK (latitude BETWEEN -90 AND 90)       
    CONSTRAINT check_longitude CHECK (longitude BETWEEN -180 AND 180)

The only requirement we applied for the email is to have an @ within the text:
    CONSTRAINT check_email_format CHECK (email LIKE '%@%')

We need to make sure that you can't send a message to yourself:
    CONSTRAINT check_sender_receiver_diff CHECK (idSender <> idReceiver)

Check that the type of service matches:
    CONSTRAINT check_service_type CHECK (type IN (1, 2, 3)),
    CONSTRAINT chk_service_logic CHECK ((type = 1 AND price IS NULL AND description_expectation IS NULL)
    OR (type = 2 AND price IS NULL AND description_expectation IS NOT NULL)
    OR (type = 3 AND price IS NOT NULL AND description_expectation IS NULL))

Individual cannot vote more than once against the same target in the same community :
    CONSTRAINT unique_vote_per_user UNIQUE (idTarget, idVoter, idCommunity)






Python : 

The Python part is in the folder "4 - Python interface". It has three files:

    main.py            : access layer to the database (psycopg2)
    User_Interface.py  : console menu application, it uses main.py
    gui.py             : Tkinter window


main.py

The connection settings (host, database, user, password) are read from the environment variables RESILIENCE_DB_HOST, RESILIENCE_DB_NAME, RESILIENCE_DB_USER and RESILIENCE_DB_PASSWORD, so that no password is written in the code.

There is one function per action of the project:

    add_individual, add_community       create an entity
    join_community, create_link         membership and links between entities
    update_geolocation                  register the coordinates of an individual
    send_message                        send a message, or a reply when id_reference is given
    add_skill, declare_skill            skill repository and skills mastered by an individual (level 1 to 5)
    propose_service                     propose a free, exchange or commercial service
    vote_opposition                     vote against the presence of a person in a community
    check_community_status              read Community_View and print ACTIVE or EXCLUDED

Each function opens a connection, runs its SQL statements with query parameters (%s) in one transaction, commits, then closes the connection. If PostgreSQL rejects the operation, the function rolls back and prints the error.

The ids are generated by the database. For example, add_individual first inserts the row in Connectable_Entity (INSERT ... RETURNING idEntity), then uses the generated id for the row of Individual. add_community works the same way.

The rules of the project are not checked again in Python: they are enforced by the constraints of the schema (valid latitude and longitude, no message to oneself, consistency between the type of a service and its price or expectation, one vote per voter against the same target in a community). A forbidden operation fails in PostgreSQL and the function only reports the error. propose_service only sets the unused fields to NULL according to the type (1 = free, 2 = exchange, 3 = commercial) before the insertion.


User_Interface.py

It is a menu loop with 12 options (0 to leave): add an individual or a community, join a community or create a link, messages, geolocation, skills and services, vote, the specialized views, the lists of individuals and communities, and a search.

The views read the SQL views Community_View, Message_View and Proximity_View. The search looks for a keyword (ILIKE) in the names of individuals and communities and in the titles of services.


gui.py

It is a Tkinter window with five tabs (creation, actions, services and skills, messages, views). It calls the functions of main.py with arguments that do not match their current signatures any more: for example add_individual(eid, name, email), while main.py now expects add_individual(name, email) because the ids are generated by the database. The console application User_Interface.py is the functional interface.
